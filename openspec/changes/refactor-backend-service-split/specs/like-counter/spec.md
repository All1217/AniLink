# Spec Delta

## Purpose

定义点赞/取消点赞与计数聚合的写入路径、时延与幂等语义，保证高并发点赞不压垮数据库，并让计数最终收敛到真实值。

## ADDED Requirements

### Requirement: 点赞幂等
同一用户对同一业务对象的重复点赞或重复取消 MUST 不改变最终状态；状态查询 SHALL 在写入后立即返回最新状态。

#### Scenario: 重复点赞
- **WHEN** 用户连续两次点赞同一个视频
- **THEN** 点赞集合只保留一份该用户，计数不重复增加

#### Scenario: 点赞后查询
- **WHEN** 用户点赞成功并立即查询点赞状态
- **THEN** 返回已点赞

### Requirement: 写路径不落库
点赞与取消点赞 MUST 只操作缓存，不产生同步数据库写入；计数由定时任务批量聚合后异步投递。

#### Scenario: 点赞请求
- **WHEN** 用户点赞
- **THEN** 请求链路只执行缓存读写，不执行数据库 UPDATE

#### Scenario: 批量聚合
- **WHEN** 聚合任务触发
- **THEN** 每个业务类型单批最多取出 30 条计数并投递一条消息，周期为 20 秒

### Requirement: 计数最终一致
数据库计数 MUST 在聚合周期后收敛到缓存中的真实值；消息重投或重复消费 MUST 幂等，消息体携带绝对计数而非增量。

#### Scenario: 计数收敛
- **WHEN** 缓存中某视频点赞数为 N 且消息被成功消费
- **THEN** 数据库计数值为 N

#### Scenario: 消息重复
- **WHEN** 同一条计数消息被消费两次
- **THEN** 数据库最终值仍为 N，不出现累加错误

### Requirement: 业务类型隔离
视频点赞与评论点赞 MUST 通过 bizType 区分聚合与消费；本次重构 MUST NOT 改变既有缓存 key 结构，避免已有点赞状态丢失。

#### Scenario: 视频与评论分别聚合
- **WHEN** 视频与评论同时产生点赞
- **THEN** 两类计数分别进入各自的聚合队列与消息路由

#### Scenario: 既有数据保留
- **WHEN** 新版本服务上线
- **THEN** 已有点赞集合与计数缓存仍可读取，不需要重建

### Requirement: 故障可恢复
消费失败 MUST 可重试且不丢失计数；服务重启后，尚未投递的计数 SHALL 在下一个聚合周期重新发送。

#### Scenario: 消费方暂时不可用
- **WHEN** 计数消费服务下线后恢复
- **THEN** 期间产生的计数在恢复后完成落库，不出现永久缺失

#### Scenario: 发送失败补偿
- **WHEN** 聚合任务发送消息时抛出异常
- **THEN** 该批计数被放回待发送集合，下一个周期重试，不永久丢失
